Three shapes of data: the log table you own, the usage cache the reader builds, and the price registry that is checked in. Only the first is ground truth.

activity_logs.db — one table, logs

One row per event. Nothing is normalised away: repository, branch, task and agent identity live on every row, so a single append is always sufficient and no writer ever has to read before it writes.

The three keys everything is built on

  • (repo_name, branch_name, task_title) groups rows into a task. Character for character — a task title that drifts by one space becomes two tasks with two separate wall clocks.
  • agent_path groups rows within a task into runs, and its / depth defines the parent-child relationship the waterfall indents and "own time" corrects for.
  • trace_id links rows into one narrative for the detail panel's trace timeline. It is the only key that is allowed to cross tasks.
The one hard invariant: each agent brackets its work with a start row and an end row carrying the same repo, branch, task and agent_path. Every duration and every idle gap is derived from those pairs. A run whose end never arrived is closed at its last event, so the work after that point simply disappears from the time views.

Indexes

The shipped file has none, which is fine at this size — the dashboard issues one unindexed full scan per load. On a large file, (timestamp) helps the read and (repo_name, branch_name, task_title) helps any grouped query you run against the file directly.

token_usage.db — one row per API request

A separate file, and separate on purpose: it is a cache. Every row is re-derivable by re-reading the agents' session transcripts, which is what makes Rebuild usage safe and why the reader never has to open the database the README calls a contract. Back up activity_logs.db; ignore this one. The DDL lives in seed/new_usage_db.py, which usage_reader.py imports rather than repeating.

ColumnTypeNotes
request_idTEXT PKThe dedupe, enforced by the schema rather than by the writer remembering. With INSERT OR IGNORE it makes re-import idempotent by construction.
session_idTEXTThe coding agent's session. Several logged agents commonly share one.
timestampTEXTISO-8601. The only thing that joins a request to a task, together with repo and branch.
model_idTEXTMatched against the registry to price the row. An id the registry does not know shows tokens and a dash for cost — never a guessed rate.
repo_name / branch_nameTEXTThe scope keys. A usage row has no task, agent or trace of its own.
input_tokensINTEGERThe uncached remainder, not the input. On a real session here it read 1,449 against a true input of 1,091,210.
cache_read_tokensINTEGERUsually the overwhelming majority of tokens and a rounding error in the bill.
cache_write_5m / cache_write_1hINTEGERKept apart because they are priced differently — 1.25× and 2× the input rate on Anthropic models.
output_tokensINTEGERIncluding reasoning tokens unless an agent reports those separately, in which case they are in extra_json.
service_tier / speedTEXTTier modifiers. batch and fast select a different price tier for the whole row.
sourceTEXTWhich parser produced the row. Surfaced in the source-transparency panel.
extra_jsonTEXT (JSON)A closed allow-list of ~10 keys, each capped at 64 characters — long enough for a model id, far too short for a sentence. agent_type lives here, and it is what makes per-agent cost possible.

A second table, watermark(parser_id, source_path, cursor, size_bytes, mtime_ns, last_run), is the staleness check: size and mtime both unchanged means the file is skipped without being opened, which is what keeps a refresh over hundreds of megabytes of transcripts cheap. cursor is deliberately opaque — the parser defines it, because a byte offset suits JSONL and would exclude any agent storing usage in SQLite or protobuf.

NULL is not zero, and the distinction survives from the parser all the way to the pixel. 0 means the agent reported zero; NULL means it does not report that counter at all. Codex has no cache-write equivalent — rendering that as 0 would claim its cache writes were free. Anything that coerces one into the other is a bug, and UsageRecord.problems() is where it gets caught.

llm_registry — the price list

Not a database: a checked-in JavaScript object generated from script/llm_registry.py. It is keyed by provider, and every price in it is USD per 1,000,000 tokens.

provider                       e.g. "anthropic"
  provider_name, provider_url
  models[]
    model_name, model_id, description
    capabilities[]               coding · reasoning · vision · long-context · tools
    latency_class                fastest · fast · medium · slow
    regional_availability[], context_window
    status                       active · preview · legacy · deprecated
    expiration_date              set once a retirement date is published
    pricing
      input_token[]              tier_order, tier_name,
      output_token[]             price_value, price_currency, price_per_qty

Four rules the file holds itself to, all of which the UI depends on:

  • Nothing is ever deleted. Superseded models become legacy, retired ones deprecated with a date — and they keep their historical prices, so a six-month-old session still costs correctly. 37 of the 102 models are retired for exactly this reason.
  • Nothing is invented. A value that cannot be verified against a fetched official page keeps its existing value.
  • The two directions are independent lists. Tier names overlap heavily but are not guaranteed to; a tier priced in one direction and not the other is normal, and no provider prices cached output at all.
  • Read price_per_qty, do not assume it. Everything is currently per 1,000,000, but a future provider quoted per 1,000 would otherwise be 1000× wrong and look entirely plausible.

A tier named intro_…_until_YYYY_MM_DD is a launch price that displaces standard until that date passes — so a session dated inside the window prices at the introductory rate and one after it does not. Claude Sonnet 5 currently has one.
