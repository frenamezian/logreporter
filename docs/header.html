Refresh stats

Refresh tells you the database was re-read. It does not tell you whether anything came back, and on a busy afternoon "did that do anything?" is the whole question. The panel at the left end of the header answers it: a count on the button, and a breakdown behind it.

It opens by itself after a Refresh that brought something back, and stays shut after one that did not — a panel that covers the page every time you press a button, to say nothing happened, gets dismissed unread and then ignored when it matters. Clicking a task drills the whole dashboard to it. Each task row carries the date of the newest log that arrived for it.

What "since" means. The count is measured from the last explicit Refresh — or from page load, or from the moment you opened a different database, whichever came last; the panel names which. Auto-poll deliberately does not reset it. Polling picks rows up five seconds after they land, so if it moved the baseline the count would be zero every time you looked; instead the badge climbs on its own between refreshes, and Refresh is what clears it. A refresh that failed read nothing, so it resets nothing.

It ignores your filters. The count is what the database gained, not what survived the filter bar — a filter that quietly swallowed new rows would make the word "picked up" a lie. Where the two differ the panel says so, in as many words, and the number above stays honest. Nothing persists across a page reload: reloading is genuinely a fresh baseline, and a stale one carried across a rebuilt database would be worse than none.

The data-source menu

  • Open activity_logs.db — picks a database anywhere on disk. Where the browser supports file handles (Chromium-based), the handle is kept so Refresh and Auto-poll can re-read it without asking again; elsewhere a plain file input is used and you re-pick the file each time.
  • Auto-poll on / off — checks the source every five seconds. For a file you opened by hand, the check is cheap: the file is only re-parsed when its modified time has changed. For the served activity_logs.db it is re-fetched each tick, with caching disabled so a stale copy can never be served.
  • Save database copy — downloads the in-memory database as a .db file. It never overwrites the file you opened.

The dot's colour is the load state: lit means a real database is loaded, grey means the bundled demo data, red means the last read failed. The line under the file name always says which, with the error text when there is one.
