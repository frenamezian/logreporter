Where the wall-clock time went, with idle treated as a first-class category rather than a residual. This is the only page whose shape follows the drill depth, and the only one where the numbers need explaining — so this topic explains them.

1 · The vocabulary

Four words carry all the arithmetic on this page. None of them are stored in the database — every one is derived from the log rows each time the page is drawn.

TermDefinition
RunOne agent working once inside one task: a start row opens it, the matching end row closes it. Its length is end − start. The same agent dispatched three times is three runs.
SegmentThe stretch between one log row and the next row of the same run. Every segment belongs to exactly one run and is attributed to the type of the log that opened it.
Wall clockFirst event to last event of a task, no matter who was working — the elapsed time a person would have watched.
IdleThe part of that wall clock covered by no run at all.

2 · How a segment gets its colour and its length

Inside a run, the rows are put in time order and each one claims the time until the next one:

run: task_executor      19:26 ───────────────────────────────── 20:57

  19:26  start     ├──────── 13m ────────┤   activity
  19:39  activity  ├─ 8s ─┤                  activity
  19:39  decision  ├─ 1s ─┤                  decision
  19:39  decision  ├──────── 12m ────────┤   decision
  19:51  issue     ├──────── 22m ────────┤   issue
  …
  20:57  end       ┤                         (point — no time)

So a log's duration is how long it was the most recent thing that agent said. An issue row followed by nothing for 22 minutes means 22 minutes of issue time, which is exactly the reading you want: the agent was stuck on it.

The mapping from log type to category is fixed: issue → issue, decision → decision, github → GitHub, and everything else — activity, start, end — → activity. A segment with no time (the closing end row, or two rows sharing a timestamp) is kept as a point: it accounts for zero time but stays visible and clickable in the waterfall, drawn as a tick.

3 · Own time versus span

A parent agent stays open while its subagents work, so its run contains theirs. Counting both would bill the same minutes twice.

lead_architect   ├─────────────────────────────────────┤  span 1h 31m
  task_executor    ├───────────────────────────────┤       span 1h 31m
    code_reviewer      ├──────┤                            span 12m
    test_writer                      ├────────┤            span 27m

Each run therefore carries two numbers, shown as SPAN and OWN:

  • Span — end − start, the whole time the agent was open.
  • Own — the span minus the union of its descendants' runs: the time it was working rather than waiting on something it had delegated. A parent's own time plus its children's spans add back up to the parent's span.

Sibling agents running at the same time are not subtracted from each other. That overlap is real concurrency, not delegation, and hiding it would misreport a genuinely parallel run as a short one.

4 · From runs to a task

A task is every row sharing the same repository, branch and title. Its numbers are built in this order:

  1. Span — earliest run start to latest run end. This is the task's wall clock.
  2. Busy — the union of all its runs. Overlapping agents are merged first, so two agents working the same ten minutes count as ten minutes of busy, not twenty.
  3. Idle — the complement: the parts of the span that busy does not cover. Wall clock = busy + idle, always.
  4. The four coloured categories — busy time apportioned across activity / issue / decision / GitHub in the same ratio as the raw segment sums. So the coloured part of a task's bar totals its busy time, and the bar as a whole totals its wall clock.
  5. Agent time — the plain sum of every run's span, overlap and nesting included.
Why apportion instead of just summing the segments? Raw segment sums are per-agent, and nested agents double-count: a parent's 22-minute wait and the child's 22-minute run are both real, but they are the same 22 minutes of the clock. Summing them would make a task's coloured bar longer than the task itself. Apportioning keeps every bar honest against wall clock while preserving the shape — which categories dominated — exactly as the segments reported it.

5 · Rolling up to branches, repositories and the whole scope

Branch, repository and page totals are plain sums of the task figures — wall clock, idle, each category, agent time, log and issue counts. Two consequences are worth having in mind:

  • A repository's wall clock is the sum of its tasks' wall clocks, not its own first-to-last span. Two tasks running the same afternoon count twice, because the question being answered is "how much task time does this repository represent", not "how long was this repository busy".
  • Idle is summed the same way, so the idle share stays comparable at every level. A gap only ever belongs to the task it sits inside; time when a repository had no task running at all is nobody's idle and is not counted.

6 · The stat cards

CardWhat it is
Wall clockSummed task wall clock for everything in scope, with the task count underneath.
Agent timeThe sum of every run span, with its ratio to wall clock and the "excl. subagents" figure — the sum of own time. The ratio is deliberately not capped at 100%: 268% of wall means agents nested and overlapped that heavily, and that is the interesting number.
IdleSummed idle, as a share of wall clock.
Issue timeThe issue category's share of busy time, with the issue row count.
GitHub timeThe GitHub category's share of busy time, as a percentage of wall clock.

7 · The bars, and what a click does

One bar per item at whatever level the drill scope sits: repositories → branches of a repository → tasks on a branch → agent runs of a task. Each bar is subdivided by whatever makes it up — the branches of a repository, the tasks of a branch, the agents of a task, the individual log rows of an agent — with a hairline between neighbours. The category order never changes, so the subdivision reveals that a block is several things without altering what the bar says. Bar lengths are scaled against the largest wall clock in view.

Click targetResult
A repository, branch or task barDrills one level deeper. The page's level is the drill depth, so the breadcrumb and the tree are the way back up — there is no separate level control to fall out of sync.
An agent bar (deepest level)There is nothing left to drill into, so it focuses that run instead: the waterfall highlights it and the run's logs are listed below. Clicking it again unfocuses.
A gaps-table rowDrills to the repository, branch and task of that gap, which brings up its waterfall.

Agent bars are indented by agent_path depth rather than being drillable, and carry "Xm own" under the span whenever the run had subagents.

8 · The waterfall

At task level the waterfall appears: one row per run, indented by agent_path, positioned horizontally by real clock time against a five-tick axis. One coloured block is one log row — it starts at that log and ends at the next log of the same run — so the waterfall is a picture of the segment arithmetic above, not a separate summary.

  • The IDLE row underneath shows the gaps no run covers, in the same horizontal frame.
  • Clicking a block opens that log in the detail panel and focuses its run. Clicking the row anywhere else focuses the run without changing the open entry.
  • With an entry open, every block of the same trace_id stays lit and the open one is outlined — so Prev / Next in trace in the detail panel walks visibly across the waterfall.
  • Logs in this run, below the waterfall, lists the focused run's rows with the stretch each one accounts for. A point row reads "—".

9 · Longest idle gaps

The closing table ranks the twenty longest gaps anywhere in scope, with the task they belong to and the clock times they span. Clicking a row drills to that task, which brings up its waterfall below.

Consequences worth knowing. A run whose end row never arrived is closed at its last event, so it contributes only the time it actually logged. A task with a single entry has zero wall clock. And time an agent spends working without logging is reported as idle — which is the honest reading, and the reason the logging contract asks agents to log when they begin waiting on something slow.
