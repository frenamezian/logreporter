One file per coding agent, found by globbing parsers/. Each one reads a single agent's private format and yields UsageRecord objects; everything downstream — the reader, the writer, the schema, the pages — knows only the record. This topic is about the two shipped native parsers, because they are the two shapes the plugin contract has to accommodate: an append-only text file, and somebody else's live SQLite database.

The contract: seven names

A parser is a module in parsers/ that exposes seven names. There is no registration list to edit, deliberately: a central registry would put every contributor's pull request in the same file, so every pull request would conflict with every other one. loader.py imports every .py in the directory that does not start with _, and a module declaring none of these names is not treated as a parser at all — that is how loader.py and conformance.py live in the same folder without a hard-coded list of the framework's own files.

NameTypeNotes
AGENT_IDstrStable key, and the value of the source column.
AGENT_NAMEstrShown in the source-transparency panel.
HOMEPAGEstrLinked from that panel.
PRIORITYintHighest wins a contested AGENT_ID; ties break on module name. Both native parsers are 100, the ccusage fallback is 1.
detect()→ boolIs this agent on this machine? Runs on every refresh, for every parser, before anything is read — so it is a path test and nothing else.
discover()→ list[Path]The files this parser owns.
parse(path, cursor)→ (Iterator[UsageRecord], str)The records appended since cursor, and the new cursor.

A module declaring some of the seven is a parser with a mistake in it, and the loader reports exactly which names are missing. A module that raises on import is skipped, logged with its traceback, and named in the dashboard — one broken community parser costs that parser and nothing else, but it never silently reads as zero.

Three optional names the reader uses if they are present, and ignores otherwise: PARSE_STATS (a counter dict — lines skipped, shapes not understood — surfaced in the source panel), UNAVAILABLE_HINT (shown when detect() is false, so "unsupported" reads as "not installed"), and exclude_agents(), which fallback adapters use to stand down for an agent that already has a native parser.

UsageRecord — the normalized output

Defined in parsers/__init__.py rather than in usage_reader.py, because parsers import the record and the reader imports the parsers; putting it in the reader would make that a cycle. Here it is a leaf that imports nothing of ours.

Three properties carry most of the design:

  • request_id is the dedupe key and the primary key of the table. The dedupe is not something the writer has to remember: with INSERT OR IGNORE it is a property of the schema. An agent with no request identity of its own must synthesize a stable id — the same input must hash the same way on every run, or re-import stops being idempotent.
  • Every counter is Optional, all the way to the browser. 0 means the agent reported zero; None means it has no such counter. problems() lives on the record so the writer and the conformance harness cannot drift apart about what "a valid record" means.
  • input_tokens is the uncached remainder, never the total input. The total is input_tokens + cache_read_tokens + cache_write_5m + cache_write_1h, computed at render time and never stored. The parser's job is only to keep the four apart.

extra_json is the one open-ended field, and it is closed by a whitelist of about ten keys in parsers/__init__.py, each value capped at 64 characters — long enough for a model id or a CLI version, far too short for a sentence. The list lives in one place and is enforced twice: by the parser, and again by usage_reader.py on the way into the database. The second gate exists so a future community parser cannot widen it by accident.

The storage mechanism

The reader's loop is four steps: load every parser, ask the ones that claim this machine for their files, skip the files whose size and mtime are unchanged, and parse the rest from their recorded cursor.

The cursor is opaque to the framework

Nothing outside a parser ever looks inside its cursor. The reader stores the string in watermark.cursor and hands it back on the next run; the parser is the only code that interprets it. Fixing it to "byte offset" in the framework would have excluded every agent that does not keep its usage in a text file — which is precisely the second parser on this page.

Both shipped parsers put their PARSE_VERSION, their AGENT_ID and their PRIORITY inside the cursor and refuse one they do not recognise, falling back to reading the file from the start. That is what makes "the meaning of what this parser emits changed, re-read everything" work without adding a column to the watermark table, and it is self-healing: an unrecognised cursor costs one full re-read, not a wrong number.

The watermark is a speed optimisation, never a correctness one

watermark(parser_id, source_path, cursor, size_bytes, mtime_ns, last_run). A file whose size and mtime both match what was recorded is not opened at all — the common case, and the one that keeps a refresh cheap over hundreds of megabytes of transcripts. Two conditions invalidate the cursor outright and force a full re-read: a file smaller than recorded was truncated or rotated, and an mtime that moved backwards means the file was replaced or restored from a backup.

The stat is taken before the parse, on purpose. If the agent appends while the file is being read, the recorded size is behind the cursor and the file gets read again next time — which costs a little time and inserts nothing. The other direction would lose the appended rows.

Getting the cursor wrong costs time, never accuracy. request_id is the primary key and every insert is INSERT OR IGNORE, so resuming too early re-reads rows that are already there and inserts nothing new. This is what makes it safe to be aggressive about skipping, and what makes Rebuild usage a complete escape hatch rather than a repair tool.

Two kinds of source

SOURCE_KIND defaults to "files": things on disk that get stat-ed, watermarked, and appended to. The alternative is "command" — a CLI that reports aggregates rather than a file you read incrementally, which is what parsers/ccusage.py is. For those the reader skips stat and watermark entirely and deletes and replaces the parser's whole source namespace on every run. That is required, not a shortcut: an aggregate row's numbers change as the day goes on, and INSERT OR IGNORE would freeze the first snapshot of the day forever. Both parsers described below are "files".

claude_code.py — appended JSONL

Claude Code writes ~/.claude/projects/<encoded-cwd>/<session-uuid>.jsonl, one JSON object per line, appended as the session runs. CLAUDE_CONFIG_DIR is honoured, because a user who moved their config would otherwise look like a user who has never run it.

Discovery is recursive — rglob("*.jsonl"), not a top-level scan. Subagent runs live one level deeper, in <session-uuid>/subagents/agent-*.jsonl, and a subagent frequently runs a different model than its parent. A top-level-only scan would omit that spend entirely while still presenting a confident-looking total. Each sidechain file has an agent-<id>.meta.json beside it; the parser reads agentType from it — one small read per file, not per line — and that single field is what makes "subagents cost 40% of this task" answerable at all. It lands in extra_json as agent_type.

A byte-offset cursor, and the partial last line

The cursor is {"parser","parse_version","priority","offset"}; offset is a byte position and resuming is a seek(). Three details are load-bearing:

  • The file is opened in binary, not text mode. A text-mode tell() returns an opaque cookie rather than a byte offset, so it could neither be compared against the file size nor stored as a resumable position.
  • A line that does not end in a newline is left unread. The agent is mid-write; the offset stays before that line so the complete version is read next time. Without this, a half-written line is either lost or parsed as garbage.
  • The file is read eagerly into a list. parse() returns (iterator, new_cursor), and the new offset is only known once the last complete line has been consumed — so it cannot be produced lazily. Session files reach about 14 MB, but on a normal refresh only the appended part is read, so the memory is bounded by one file's growth between refreshes rather than by history.

Dedupe, because one response is many lines

One API response is written as several lines — one per content block — each carrying a byte-identical usage object. Summing lines overcounts. In the fixture committed to this repository, 44 lines carrying a usage object collapse to 12 distinct requests, and summing them instead inflates the total by 3.36×: 3,710,184 tokens against a true 1,105,582.

The dedupe is belt-and-braces: a seen set within a single parse pass, and request_id being the table's primary key across passes. Lines with no requestId get a synthetic one — sha256(sessionId | uuid | filename), truncated and prefixed syn_. Stability is the entire requirement: the same line must hash the same way on every run or INSERT OR IGNORE stops making re-import idempotent.

Two kinds of line are dropped rather than emitted. API-error placeholders — isApiErrorMessage, or a model of <synthetic> — represent no spend, and emitting them would put <synthetic> in front of the user as an unpriceable model with a "go add it to the registry" hint, which is advice that makes no sense. Lines with no usable timestamp are dropped too. Both are counted in PARSE_STATS rather than swallowed, and the counters are arranged so they reconcile: usage_lines = skipped_api_errors + skipped_no_timestamp + deduped_lines + records.

The cache-write TTL split

Modern transcripts carry usage.cache_creation as an object, and the two ephemeral tiers map straight across:

cache_creation.ephemeral_5m_input_tokens  → cache_write_5m
cache_creation.ephemeral_1h_input_tokens  → cache_write_1h

Older transcripts, written before the one-hour cache existed, carry only the cache_creation_input_tokens total. Every cache write back then was five-minute ephemeral, so mapping it to cache_write_5m is a fact about the old format rather than a guess about the TTL — but it is flagged in extra_json as cache_write_ttl: "implied_5m" either way, because which tier applies changes the price (1.25× and 2× the input rate).

Why input_tokens is so small

Anthropic's input_tokens is the uncached remainder. In the same fixture it reads 1,449 against a true input of 1,091,210 — 1,449 + 804,539 + 0 + 285,222 — which the bare field understates by 753×. A parser that maps that field to "input" and stops produces a number that is wrong by nearly three orders of magnitude and looks entirely reasonable.

What is deliberately not extracted

message.content: the prompts, the replies, tool arguments, file contents and whatever secrets passed through them. The parser reads the numeric counters and a short envelope — isSidechain, entrypoint, version, effort, each an enum-like token or a version string — and nothing else in the line is ever touched. Repository attribution is derived from the transcript's cwd by walking up to the nearest .git in the same way log_activity.py does (a linked worktree reports the main repo, a submodule reports itself), as a cached stat walk rather than a subprocess: git rev-parse is about 70 ms on Windows and a history holds hundreds of distinct directories.

antigravity.py — a SQLite database per conversation

Not in the IDE's VS Code storage, which is where you would look first and where there is nothing. The agent half of Antigravity is a separate language-server process with its own data directory, named after the --app_data_dir it was launched with:

~/.gemini/antigravity-ide/conversations/<cascade-uuid>.db   (current)
~/.gemini/antigravity/conversations/<cascade-uuid>.db       (older install)

Each file is a SQLite database for one conversation. gen_metadata(idx, data, size) holds one row per LLM request, data being a raw protobuf blob with no base64 wrapper. trajectory_metadata_blob holds the workspace, git remote and branch; trajectory_meta holds the ids.

The blob wraps one exa.cortex_pb.ChatModelMetadata in field 1. Field 4 of that message is usage, an exa.codeium_common_pb.ModelUsageStats, and the counters are its fields 2 (input_tokens), 3 (output_tokens), 4 (cache_write_tokens), 5 (cache_read_tokens), 9 (thinking_output_tokens), 10 (response_output_tokens) and 11 (response_id). The field names are not inferred from value shapes: both schemas are compiled into the IDE bundle as protobuf FileDescriptorProtos, so they are the real ones. Three things were then checked against every request on the machine this was written on — 7,679 of them across 69 conversations:

  • thinking + response == output held on all 7,679, so field 3 is the output total and 9 and 10 are its split. Summing all three would double-count output. The thinking figure is reported separately in extra_json as reasoning_output_tokens.
  • response_id was unique across all 7,650 rows that had one, which is what makes it usable as the dedupe key rather than something synthesized. The 29 rows without one fall back to antigravity:<session>:<idx>, stable for the same conversation and row.
  • Field 4 never appeared.

The parser reaches for named fields and never walks the tree. Field 1.9.10 of the same blob is a context breakdown — section names, the user's rule and skill names, tool names, a token count each. It is not message content, but it is close enough that none of it belongs in a usage database, so nothing outside the map above is ever decoded.

An idx cursor, and why the sentinel is −1

gen_metadata.idx is the table's INTEGER PRIMARY KEY and rows are appended one per request, so the whole of the cursor is "the idx to resume after" and the whole of the query is WHERE idx > ? ORDER BY idx. The read-everything sentinel is −1, not 0: idx starts at 0, so WHERE idx > 0 would silently drop each conversation's very first request. That is one whole request per conversation missing — a shortfall no total would show as obviously wrong.

A conversation with no rows at all leaves nothing to resume after, so the parser returns a NULL cursor and the file is read from the start next time, which is the wanted behaviour rather than an oversight.

Read-only access to a live database

The connection is a file:…?mode=ro URI against the live file. This is another process's data and there is 745 MB of it, so copying it on every refresh is out of the question; and opening it read-write could let SQLite checkpoint or recover — writing into a running agent's store. A read-only open still updates <uuid>.db-shm, SQLite's shared-memory index, but that file is ephemeral, rebuildable, and rewritten by Antigravity constantly. The two files that hold data are left untouched.

Why discover() returns the -wal path

These databases are in WAL mode and Antigravity holds them open for weeks at a time. A new request therefore lands in <uuid>.db-wal and the .db file's size and mtime do not move at all. The reader skips a file whose size and mtime are unchanged — so returning the .db path would mean every new request stayed invisible until Antigravity happened to checkpoint. This is the case where the watermark's speed optimisation would have become a correctness problem, and the fix is at the parser's end, not the framework's: discover() hands back the path that actually changes.

It is not a rare corner. On the development machine this was written against, 59 of the 95 conversation databases had a live WAL at the time of writing. When a WAL is checkpointed away the .db path is returned instead; that is a new watermark key and costs exactly one re-read, which INSERT OR IGNORE on the response id absorbs.

repo_name comes from the git remote, not the folder

The workspace blob carries both the workspace folder URI and the git remote, and they differ in practice — a folder called Playground-Harness cloned from frenamezian/Playground. The parser takes the repository name from the remote, because that is what log_activity.py records, and attribution joins a usage row to a task on repository and branch. Taking the folder name would produce rows that are correct in isolation and attributable to nothing. The folder name is the fallback, for a workspace with no remote at all.

Cache writes are NULL, not 0

ModelUsageStats field 4 is cache_write_tokens — Antigravity simply never writes it. It was absent in all 7,679 real requests checked. So cache_write_5m and cache_write_1h are both NULL for every Antigravity row. Reporting 0 would claim its cache writes had been measured and found free, which is a different and false statement. service_tier and speed are NULL for the same reason: this agent does not report them.

The one place this parser cannot simply pass a value through is the model id, and it is worth setting out because the obvious source is the wrong one. Field 19 looks like a model id — gemini-3-flash-a, claude-sonnet-4-6 — but it is an alias, and it is not one-to-one with anything: gemini-3-flash-a appears against model enums 1020 and 1132, while enum 1020 appears as gemini-3-flash-a, gemini-3-flash-b and gemini-default. The -a/-b pairs run concurrently on the same enum, so they read as experiment arms rather than models.

The identity is the enum in field 1.4.1, which the IDE resolves through a catalog in its own storage (antigravityUnifiedStateSync.userStatus, field 33 cascade_model_config_data). The parser deliberately does not use it. That catalog is a server-provided snapshot and the enums are renumbered over time: enum 1133 meant “Gemini 3.5 Flash (High)” in the older install’s catalog, is absent from the current one where 1084 now holds that label, and 1132 carried the same label in July while appearing in neither. Resolving today’s catalog against rows written in May would label them confidently and wrongly.

So the parser resolves the id itself, in three steps, and records which one answered in extra_json.model_id_source:

  1. recorded — field 21, model_display_name. The name Antigravity itself resolved, written at the time of the request, so it cannot become retrospectively wrong. Present on 42% of requests and effectively all recent ones.
  2. enum_table — the parser’s own _ENUM_NAMES, for the older requests written before field 21 existed.
  3. alias — otherwise the field 19 string, unchanged and unpriced.

_ENUM_NAMES is not the catalog by another route, and the difference is the whole point. It is observed history, pinned in the source with the window it was observed in, and consulted only for a request carrying no name of its own. Those requests are finished and frozen, so nothing can shift underneath them; if an enum is ever reused, the new requests will carry field 21 and step 1 wins. An enum nobody has observed falls through to step 3 and stays unpriced — the right direction to fail in, because cost-model.js then shows tokens and a dash rather than a guessed rate, and names the id in its unknown-models set.

The name is then split: “Gemini 3.5 Flash (Medium)” becomes the registry id gemini-3.5-flash plus extra_json.effort of Medium. The suffix is a reasoning-effort setting, not a different model — the same tokens at the same price — so it informs the reader without ever moving the cost. The match has to be exact, because lookupModel() is a map lookup that does no normalising of its own.

Seven observed enums collapse to four registry ids this way, which took Antigravity from 716 of 11,795 requests priced to all of them. model_id_source is what lets the interface show a derived name as derived rather than passing it off as recorded — the same contract cache_write_ttl: "implied_5m" has in the ccusage adapter. The request table on the Metrics page marks those rows †, with the reason in the mark’s tooltip and a count in the footnotes; log-usage.js is the only component that reads extra_json, and it memoises the parse onto the row because otherwise it would be tens of thousands of JSON.parse calls per render.

Changing what a parser emits for rows already imported

Worth knowing before editing any parser, because two of the mechanisms above conspire against it. Bumping PARSE_VERSION invalidates that parser’s stored cursors, but it does not rewrite existing rows: the reader skips a file whose size and mtime are unchanged without ever consulting the cursor, and rows are written INSERT OR IGNORE on request_id, so re-reading an already-imported request changes nothing. Both behaviours are deliberate — they are what make a wrong cursor cost time instead of correctness.

Rewriting imported rows therefore needs the escape hatch, python usage_reader.py --rebuild, which drops the cache and every watermark and reads the corpus again. That is safe precisely because token_usage.db is a cache and nothing else: it is re-derivable from the agents’ own session files at any time, which is also why nothing that cannot be re-derived — a manual correction, for instance — may ever be stored in it.

Fixtures

A pull request without a fixture is not mergeable, and the reason is not test coverage. A parser can only be reviewed by someone who has that agent installed — otherwise the reviewer is reading code against a file format they have never seen and taking the contributor's word for it. A redacted fixture plus its expected output turns that into something anyone can run in two seconds on any machine, with no agent installed.

parsers/tests/<agent_id>/
    fixture.*              a small, redacted session (conformance rejects > 512 KB)
    expected.json          the records the parser must produce
    expected_totals.json   hand-counted totals, and a note saying why they are right

expected_totals.json is the one that carries the weight, and its _why field is not decoration: generating expected.json from the parser is fine — it pins behaviour against regressions — but a fixture that only pins a parser to its own output would happily pin in a 3.4× overcount forever. python -m parsers.conformance checks totals against the hand-count, records against expected.json, that parsing twice is identical, the UsageRecord invariants, that NULL survives as NULL, that the cursor round-trips, and that nothing long enough to be message content reached a field. Every parser that loaded is checked, not only the ones detect() claims — a contributor on Windows must be able to run conformance for a parser whose agent only exists on macOS, which is the entire point.

One is scrubbed; the other is constructed

The two fixtures here were made in different ways, and the difference is worth being honest about.

claude_code's is scrubbed from a real session. python -m parsers._template scrub is a whitelist: it keeps the handful of keys a parser reads and drops everything else, including the whole message body. A blacklist of "sensitive-looking" keys would let the next format change quietly reintroduce a field nobody thought to ban. It is real data, so it proves the field map as well as the arithmetic.

antigravity's is constructed by parsers/tests/antigravity/make_fixture.py, which writes the same protobuf shape with invented contents — every number, id, path, repository and branch made up, response ids included. Scrubbing was not an option: the rows are protobuf blobs with no field names in them, so "keep these keys" has nothing to match on, and scrubbing would have meant re-encoding the message anyway. And it does need scrubbing — every real blob carries that context breakdown naming the user's rules, skills and tools, and a fixture is committed forever, so the safe thing is a blob that never contained it.

What that buys: the numbers in expected_totals.json were chosen by hand before the parser ever ran, so "hand-counted" is literally true and a regression that inflates a total fails there. What it costs, and this is the real risk: it cannot prove the field map is right. A fixture encoded by the parser's own author agrees with the parser even if both are wrong about Antigravity. That is why the map was pinned down separately — from the protobuf descriptors in the IDE bundle, and from the three invariants checked against 7,679 real requests. The fixture pins the parser's behaviour; those checks pinned its premises. The five rows cover a request with no cache read, one with a cache read, a model that reports no thinking split, a request with neither a response id nor a model string, and a step that ran no model at all and must produce no record.
