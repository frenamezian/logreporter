The dashboard issues exactly three statements. Everything else — filtering, grouping, every duration, every cost — is computed in JavaScript over their results.

-- read: sql.js, on load, on Refresh, on every poll tick
SELECT * FROM logs ORDER BY timestamp DESC;

-- delete: serve.py, after confirmation, in chunks of 500 ids
DELETE FROM logs WHERE id IN (?, ?, …);

-- usage: sql.js, from the second database, when it exists
SELECT * FROM token_usage ORDER BY timestamp;

Filtering in SQL was rejected deliberately: round-tripping through WASM per keystroke is slower than filtering an array, and a single read keeps the file lock brief while agents are appending. The delete runs on the server rather than in the page because sql.js only holds a copy of the bytes — a delete applied there is discarded by the next read.

The usage read is unconditional and unfiltered for the same reason, with one addition: it is preceded by a HEAD request. The cache is tens of megabytes and the auto-poll runs every five seconds, so without comparing Last-Modified and Content-Length first, polling would re-download the whole file twelve times a minute to discover nothing had changed. There is no join between the two databases — usage is attributed to tasks in memory, by repository, branch and a timestamp inside the task's span.

Concurrency

Both the writer (log_activity.py) and the delete endpoint (serve.py) open the database in WAL mode with a 10-second busy_timeout, plus a retry loop for the rare lock that outlives it. The delete path additionally checkpoints TRUNCATE, because the dashboard re-reads the main database file over HTTP and sql.js cannot see a -wal sidecar — a delete still sitting in the WAL would reappear on the very next read and look like the delete had failed.

Querying the file yourself

These mirror what the pages show, closely enough to sanity-check them.

-- run spans per agent — the basis of every duration.
-- NB: this is the coarse version. The dashboard splits an agent's rows
-- into one run per start/end pair, so an agent dispatched three times
-- gets three rows there and one row here.
SELECT repo_name, branch_name, task_title, agent_path,
       MIN(timestamp) AS started, MAX(timestamp) AS ended,
       COUNT(*)       AS entries
FROM logs
GROUP BY repo_name, branch_name, task_title, agent_path
ORDER BY started;

-- task wall clock, newest first
SELECT repo_name, branch_name, task_title,
       MIN(timestamp) AS started, MAX(timestamp) AS ended,
       COUNT(*) AS entries,
       SUM(log_type = 'issue') AS issues
FROM logs
GROUP BY repo_name, branch_name, task_title
ORDER BY ended DESC;

-- unresolved issues, worst first
SELECT timestamp, repo_name, branch_name, agent_name, log_title, error_details
FROM logs
WHERE log_type = 'issue' AND (resolved_by IS NULL OR resolved_by = '')
ORDER BY CASE log_level WHEN 'error' THEN 0 WHEN 'warning' THEN 1 ELSE 2 END,
         timestamp DESC;

-- git activity by action. The UI reads the action out of tags AND title,
-- in this order, and drops rows that match none of them.
SELECT CASE WHEN tags || ' ' || log_title LIKE '%pull%'   THEN 'pull'
            WHEN tags || ' ' || log_title LIKE '%push%'   THEN 'push'
            WHEN tags || ' ' || log_title LIKE '%commit%' THEN 'commit'
            WHEN tags || ' ' || log_title LIKE '%add%'    THEN 'add'
            WHEN tags || ' ' || log_title LIKE '%delete%' THEN 'delete'
            END AS action, COUNT(*) AS n
FROM logs WHERE log_type = 'github' GROUP BY action ORDER BY n DESC;

-- runs that never closed: the rows that silently cost you time
SELECT repo_name, branch_name, task_title, agent_path,
       SUM(log_type = 'start') AS starts, SUM(log_type = 'end') AS ends
FROM logs
GROUP BY repo_name, branch_name, task_title, agent_path
HAVING starts <> ends;

Timestamps are UTC text and sort lexically, so MIN/MAX and BETWEEN behave correctly without any date function.

Querying the usage cache

Against token_usage.db. These stop short of cost on purpose — prices live in the registry, not in this file, so any cost figure you compute here is a second rate table that will drift.

-- where the tokens went, by model. Note SUM ignores NULL, so a counter
-- no agent reports sums to NULL rather than to a misleading 0.
SELECT model_id, COUNT(*) AS requests,
       SUM(input_tokens)      AS fresh_input,
       SUM(cache_read_tokens) AS cache_read,
       SUM(cache_write_5m) + SUM(cache_write_1h) AS cache_write,
       SUM(output_tokens)     AS output
FROM token_usage GROUP BY model_id ORDER BY requests DESC;

-- the shape of the bill, per branch: cache reads dominate the count and
-- cache writes dominate the cost, which no blended total will show you.
SELECT repo_name, branch_name, COUNT(*) AS requests,
       ROUND(100.0 * SUM(cache_read_tokens) /
             NULLIF(SUM(COALESCE(input_tokens,0) + COALESCE(cache_read_tokens,0)
                      + COALESCE(cache_write_5m,0) + COALESCE(cache_write_1h,0)
                      + COALESCE(output_tokens,0)), 0), 1) AS pct_cache_read
FROM token_usage GROUP BY repo_name, branch_name ORDER BY requests DESC;

-- which parser produced what, and which agents reported no cache writes
-- at all (NULL, not zero — the distinction the whole pipeline preserves)
SELECT source, COUNT(*) AS rows,
       SUM(cache_write_5m IS NULL AND cache_write_1h IS NULL) AS no_cache_write
FROM token_usage GROUP BY source;

-- per-subagent usage. agent_type is the first-party tag the coding agent
-- records; without it a request attributes to the task's root agent.
SELECT json_extract(extra_json, '$.agent_type') AS agent_type,
       COUNT(*) AS requests, SUM(output_tokens) AS output
FROM token_usage GROUP BY agent_type ORDER BY requests DESC;

-- a request that cannot be priced: the registry has no such model_id
SELECT DISTINCT model_id FROM token_usage WHERE model_id IS NOT NULL;
-- …then check each against script/llm_registry.py

To reconcile a query here against a task on the Metrics page, remember the join is not in SQL: a request belongs to a task when its repository and branch match and its timestamp falls inside that task's [start, end] span. Requests matching no span are the Unattributed bucket; requests inside two overlapping spans are split evenly between them, which SQL alone will not reproduce.
