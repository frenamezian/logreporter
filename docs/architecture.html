A static page over a local SQLite file, plus a small Python server whose only job is to own the file. No build step, no framework, and one network dependency: the CDN fetch for the SQLite engine.

The files

index.html          loads everything, in order, as plain <script> tags
style.css           all styling; design tokens at the top

script/
  sample-logs.js    bundled demo rows (fallback data source)
  time-model.js     runs, segments, gaps, task/branch/repo totals
  filters.js        applyFilters, drillRows, unique
  db.js             sql.js loading, open/read/delete/export
  app.js            window.LogApp — the whole application state

components/         one custom element each
  log-component.js  base class + esc/fmt/bar/typeDot helpers
  log-header.js     header row and the data-source menu
  log-filters.js    filter panel + navigation tree
  log-tree.js       Hierarchy page

  log-help.js       this guide (article + outline)

docs/               one HTML fragment per help topic, plus img/

The data flow

activity_logs.db  (agents append via log_activity.py)
      │
      │  fetch on load / Refresh / poll tick, or a file the user picks
      ▼
sql.js (SQLite compiled to WASM, loaded from CDN)
      │  SELECT * FROM logs ORDER BY timestamp DESC
      ▼
state.rows          every row, as plain objects
      │
      ├─ applyFilters(rows, filter)      → state.filtered
      │        │                              └─ buildModel → state.treeModel
      │        │                                 (the sidebar tree: siblings stay
      │        │                                  visible, so it ignores the drill)
      │        ▼
      └─ drillRows(filtered, drill)      → state.inScope
               │
               └─ buildModel(inScope)    → state.model
                        tasks · runs · segments · gaps · totals
                                │
                                ▼
                  five pages + the detail panel render from it

The database is read once per load or poll and never queried per view: every page is a pure function of the row array and the two derived models. That is what keeps interaction instant, and it is why filtering was kept out of SQL — see Queries.

Rendering

There is no virtual DOM. LogApp.render() dispatches a logapp:update event; every component extending LogComponent listens, rebuilds its own innerHTML from render(), and re-attaches its handlers in attach(). LogApp.update() is recompute() followed by render() — the distinction matters: state that only affects appearance (page, open panels, selected run) calls render(), while anything that changes which rows are in scope calls update().

Three places deliberately patch the DOM instead of re-rendering, and each has a reason:

  • Hierarchy row open/close — a full re-render would replace the element between the two clicks of a double click, so dblclick would never fire. Entry rows are also built lazily here, the first time a task is opened.
  • The help outline's search — filtering repaints only the results under the input, so the caret is never disturbed.
  • Filter dropdowns and the maintenance card — they call their own refresh(), which re-renders that component alone.

Text inputs that survive a background re-render (the filter search, the guide search) keep their draft on LogApp.state and restore focus and caret in attach().

Writes

A page cannot write to a file it fetched over HTTP, so deletion is posted to serve.py, which owns activity_logs.db and issues a row-level DELETE against it. Whole-file save-back was rejected: agents in several repositories append continuously, and writing a mutated image over the file is last-writer-wins. Without serve.py the delete falls back to the in-memory copy and is flagged as not persisted. Save database copy exports the in-memory bytes as a download and never touches the original.

Dependencies

sql.js 1.10.3 from cdnjs — the script and its .wasm — and nothing else. No framework, no charting library, no date library, no icon package, no CSS framework. Bars, the timeline and the waterfall are DOM elements with percentage widths; timestamps use native Date; exports use Blob and an object URL. To run fully offline, vendor sql-wasm.js and sql-wasm.wasm next to the page and point the loader's locateFile at them.

index.html carries a ?v= query on every asset. Bump it when shipping a change: without it browsers keep serving a cached copy and the dashboard silently runs last week's code. The help fragments have their own version constant in log-help.js.
