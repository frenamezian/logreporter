A static page over local SQLite files, plus a small Python server whose only job is to own them. No build step, no framework, and one network dependency: the CDN fetch for the SQLite engine.

There are two databases and one generated file, and their natures differ. activity_logs.db is append-only ground truth that several agents write to continuously and nothing can reconstruct. token_usage.db is a cache, re-derivable at any time by re-reading the agents' own session transcripts. script/llm_registry.js is neither — it is a generated price list, checked in, refreshed by hand.

The database is read once per load or poll and never queried per view: every page is a pure function of the row array and the two derived models. That is what keeps interaction instant, and it is why filtering was kept out of SQL — see Queries.

The second flow: token usage

Usage is observed, not logged. Nothing was added to the logging contract and no agent was asked to report anything — the numbers come from the session transcripts coding agents already write.

~/.claude/projects/**.jsonl   (and whatever other agents write)
      │
      │  usage_reader.py, on demand or via POST /api/refresh-usage
      ▼
parsers/<agent>.py            one file per agent, found by globbing
      │  each yields UsageRecord objects
      ▼
token_usage.db                INSERT OR IGNORE on request_id
      │
      │  fetch, HEAD-checked first — the file is tens of MB
      ▼
state.usage                   every row, as plain objects
      │
      └─ scopeUsage()   → state.usageInScope
               joined to tasks in memory by (repo, branch, timestamp-in-span)
                                │
                                ▼
                    Metrics · Where time goes

The two pipelines meet only in the browser, and only in memory. There is no join in SQL and no foreign key between the files — a usage row carries a repository, a branch and a timestamp, and that is the entire basis on which it is attributed to a task. The consequences of that (overlapping spans, unattributed rows, per-agent attribution) are on the Metrics page topic.

Two properties are worth stating because they are what make a rebuild safe. request_id is the primary key, so re-import is idempotent by construction rather than by the writer remembering to check — a wrong watermark costs time, never correctness. And every counter is nullable the whole way through: NULL means the agent does not report that counter, 0 means it reported zero. Codex has no cache-write equivalent, and rendering that as 0 would claim its cache writes were free.

The third input: the price registry

script/llm_registry.js is generated from script/llm_registry.py by seed/py2js_registry.py. Edit the Python and regenerate; editing the JavaScript directly means the next refresh silently discards the change. Both files carry the update prompt that refreshes them.

Two modules read it, and they must not be merged:

  • cost-model.js prices a request. It resolves a counter to the one rate that applies, walking a fallback chain — cache_read → cached_input → standard — because providers name the same tier differently and one that does not discount cache reads should price them at the full input rate.
  • model-catalog.js presents the list. It reads tiers exactly as stored, because on a rate card the absence of a tier is the fact worth reporting. A cache column that fell back to the standard rate would tell the reader that provider caches for free.
Cost is derived at render time, never stored. There is no cost column in token_usage.db and no second rate table anywhere. This mirrors the rule the project already holds for time: durations are recomputed from the start/end pairs on every draw. A stored cost silently becomes a lie the day a provider changes its prices, and nothing in the file would say so; a derived one is corrected by regenerating the registry.

Rendering

There is no virtual DOM. LogApp.render() dispatches a logapp:update event; every component extending LogComponent listens, rebuilds its own innerHTML from render(), and re-attaches its handlers in attach(). LogApp.update() is recompute() followed by render() — the distinction matters: state that only affects appearance (page, open panels, selected run) calls render(), while anything that changes which rows are in scope calls update().

Three places deliberately patch the DOM instead of re-rendering, and each has a reason:

  • Hierarchy row open/close — a full re-render would replace the element between the two clicks of a double click, so dblclick would never fire. Entry rows are also built lazily here, the first time a task is opened.
  • The help outline's search — filtering repaints only the results under the input, so the caret is never disturbed.
  • Filter dropdowns and the maintenance card — they call their own refresh(), which re-renders that component alone.

Text inputs that survive a background re-render (the filter search, the guide search) keep their draft on LogApp.state and restore focus and caret in attach().

Writes

A page cannot write to a file it fetched over HTTP, so deletion is posted to serve.py, which owns activity_logs.db and issues a row-level DELETE against it. Whole-file save-back was rejected: agents in several repositories append continuously, and writing a mutated image over the file is last-writer-wins. Without serve.py the delete falls back to the in-memory copy and is flagged as not persisted. Save database copy exports the in-memory bytes as a download and never touches the original.

Usage has the same shape of problem for a different reason: the browser cannot read ~/.claude/projects at all. Refresh usage and Rebuild usage post to serve.py, which runs the reader and answers with its report; the page then re-fetches token_usage.db. Without serve.py both are unavailable and say so — the rows already loaded stay valid, only the re-import is gone. Rebuild is safe in a way a log delete never is: the file is a cache, so the worst case is the time it takes to read the transcripts again.

Dependencies

sql.js 1.10.3 from cdnjs — the script and its .wasm — and nothing else. No framework, no charting library, no date library, no icon package, no CSS framework. Bars, the timeline and the waterfall are DOM elements with percentage widths; timestamps use native Date; exports use Blob and an object URL. To run fully offline, vendor sql-wasm.js and sql-wasm.wasm next to the page and point the loader's locateFile at them.

index.html carries a ?v= query on every asset. Bump it when shipping a change: without it browsers keep serving a cached copy and the dashboard silently runs last week's code. The help fragments have their own version constant in log-help.js.
