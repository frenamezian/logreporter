LogReporter is a single static page that reads an agent activity log — a SQLite file, activity_logs.db — and turns it into six views of the same rows. There is no upload and no server-side query: the file is parsed in the browser and every page is computed from the rows held in memory.

If you have not set it up yet, Installation is the next topic: clone, make a database, serve it.

What LogReporter assumes about your work

Every view here is built on one shape: repository → branch → task → agent, with subagents nested under the agent that dispatched them. The navigation tree is literally those four levels, and the drill-downs, the filters and the time views all follow them.

That is a modelling choice, not a law of software development, and it is worth knowing before you wire anything up. It is what makes two of the more useful numbers possible: own time exists because there is a hierarchy to subtract a subagent's work along, and cost per agent exists because each request can be traced to a place in that hierarchy. Flatten the model and both go with it.

It fits work that decomposes hierarchically — a lead agent taking a task and dispatching subagents at it. Some real ways of working fit it less well:

  • Cross-cutting changes. One logical task touching three repositories becomes three disconnected subtrees, because repository is the root.
  • Peer agents. agent_path is a parent-child chain, so two agents collaborating as equals have no honest path — one ends up arbitrarily nested under the other.
  • Loops. Review → fix → re-review, or red-green-refactor, is a cycle. The tree is acyclic and the timeline is linear, so a loop flattens into an undifferentiated run of rows.
  • Continuous sessions. Interactive work that wanders has no natural task boundary, and an invented one is worse than none because it looks real.

None of that stops you logging the work — every row still lands, and every page still counts it. It means the tree will represent it awkwardly. Two fields carry what the tree cannot: trace_id and parent_trace_id form a general graph rather than a hierarchy, and tags is free-form and searchable, so an orthogonal dimension costs nothing to add — #component:auth, #loop:review-cycle.

The practical consequence is in Installation: these four fields come from your agents' prompts, nothing validates them, and a wrong value produces a confident wrong tree rather than an error.

Loading your log

When the page is served from the repository — start_LogReporter.bat, or python serve.py — it fetches the activity_logs.db sitting next to it on startup, so you are looking at real rows immediately. The data-source button in the header reads activity_logs.db and the dot beside it is lit.

To read a database somewhere else:

  1. Open the data-source button in the header.
  2. Choose Open activity_logs.db and pick your file (.db, .sqlite, .sqlite3).
  3. The button takes the file's name and the row count in the header updates. Every page now reflects your data.
  4. Turn on Auto-poll if agents are still writing — the source is checked every five seconds, and a file you picked yourself is only re-parsed when its modified time has changed.

If the default database cannot be fetched — the page was opened over file://, or the file is missing — LogReporter falls back to a small bundled demo dataset so every page still has something in it. The dot turns grey and the data-source menu says why.

What each page answers

PageThe question it answers
HierarchyWhat work exists, and how does it nest? Repository → branch → task → the individual log entries.
ChronologyWhat happened, in the order it happened, including the stretches when nothing was logged.
Where time goesWhere the wall-clock time went — which agent, which category, and how much of it was nobody working.
MetricsCounts and distributions over the current scope, plus the issues still open — and what the work cost in tokens and money.
Models & pricingWhat every model costs per million tokens. The one page that reads no logs at all.
MaintenanceWhat is stored, and removing or exporting part of it.

The two things that scope every page

Filters (top of the left panel) narrow the rows. The navigation tree (below them) drills into one repository, branch, task or agent. Both apply to every page at once, and the breadcrumb above the content always shows the drill. Changing a filter clears the drill; drilling never changes a filter.

A good first pass: leave the filters empty, skim Hierarchy to see which repositories carry the work, click Time → on the task that looks expensive, and read its waterfall on Where time goes.
