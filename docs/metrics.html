Counts and distributions over the same filter and drill scope as every other page — nothing here is computed over the whole database unless the scope is the whole database.

The four cards

Task counts by state — Open (pending or in progress), Completed, Failed — and total Idle time. A task's state is the status on its last end row; a task with no closing row at all counts as open.

Left column — distributions

  • Entries by log type — how many rows of each type are in scope, largest first, each in its category colour.
  • GitHub operations — github rows broken down by git action. The action is read from the row's tags and title: pull, push, commit, add, delete. Rows with no recognisable action are left out rather than bucketed as "other".
  • Median task duration by repository — the median of the tasks' wall-clock times. Median, not mean, because one abandoned task that ran overnight otherwise dominates the number.

Bars are scaled against the largest value currently in view, not a fixed maximum, so a distribution stays legible whether the scope holds forty rows or forty thousand. Empty categories are dropped rather than drawn as zero-width bars.

Right column — what needs a person

  • Open issues and escalations — every issue row in scope with no resolved_by set, as cards carrying the repository and branch, the title, the description and the level. Clicking a card is the one deep link on this page: it switches to Hierarchy, expands the repository, branch and task around that row, and opens it in the detail panel.
  • Agent time — total run span per agent_path, the twelve largest, with the number of runs alongside. A nested path is listed on its own line, so a parent and its subagent both appear and their times overlap by design — see Where time goes for why.
Everything on this page is read-only. It reports the scope; it never sets it. Drill to a branch and "median task duration by repository" shows exactly one row — that is correct, not a bug.

Token usage and cost

Below the distributions, the same scope again — this time measured in tokens and money. Usage is observed, not logged: it is read from the session transcripts your coding agents already write, so it works on history that predates this feature and log_activity.py never had to change. Nothing here asks anything of your agents.

Tokens ⇄ Cost

The toggle at the top right of the section redraws the same layout against one measure at a time. It exists because tokens and cost differ by six orders of magnitude, and putting them on one axis would draw a correlation that is not in the data.

Rows keep their position when you toggle. The ranking is ordered by tokens in both views, so a row that is 3% of the tokens and 20% of the bill stays put and visibly changes length. That means the cost view is not always descending — which is the finding, not a rendering fault. From a real session in this repository:

SegmentShare of tokensShare of cost
Cache read72.8%11.1%
Cache write25.8%78.8%
Output1.3%9.9%
Fresh input0.1%0.2%

Cache reads dominate the token count and are nearly free; cache writes are a quarter of the tokens and four-fifths of the bill. A blended "tokens" number hides that completely.

The four tiles

  • Total tokens / Total cost — everything in scope.
  • Input (incl. cache) — the real input: fresh input plus cache reads plus cache writes. The agent's own input_tokens field is only the uncached remainder; on the sampled session it read 1,449 against a true input of 1,091,210, understating it by 753×. The tile names both numbers so the difference is visible rather than assumed.
  • Output — including reasoning tokens where an agent reports them separately.
  • Saved by cache — what the cache-read tokens would have cost at the model's full input rate, minus what they did cost. It holds its slot in both toggle positions and is always a currency value, because "saved tokens" is not a meaningful quantity: the tokens were read either way, only the price changed. It is not a discount on the total above — that total is already net of it.

Composition, rankings and the table

  • The stacked bar splits the scope four ways — cache read, cache write, fresh input, output — with every segment directly labelled, because colour alone stops being comfortable at four series. A segment too small to see keeps a minimum width, so the four never change shape between measures.
  • Rankings group by repository, branch, task or model. Bars are one hue in steps: they encode magnitude, not identity. The step follows the value, not the row's position, so filtering out the largest row never repaints the survivors.
  • The table lists every row behind the charts with each counter in its own column, sortable, digits aligned. It is both the accessibility path and the honest one — with four token classes plus a cost, some readers need the numbers.

Unattributed

A usage row belongs to a task when its repository and branch match and its timestamp falls inside that task's span. Rows matching no span are counted as Unattributed and shown, not dropped: that is agents working without bracketing a task, which is a real finding — the same position the idle model takes about time nobody logged. Rows falling inside two overlapping spans (concurrent agents on one branch) are split evenly between them, and the page says how many.

Sources

The panel on the right lists, per agent, which parser read it, how many files were scanned, how many were skipped as unchanged, and anything that failed to load. It is small, and it prevents the worst failure mode this feature has: a confident total that is quietly partial. A parser that failed to load is named there, because its agent's tokens are missing from every number on the page.

Only the filters that a usage row can answer are applied to it — repository, branch and date. A usage row is not a log entry, so it has no log type, level, status or agent path to filter on. The section header names any active filter it cannot honour rather than quietly showing a total that does not match your filters.

How usage aggregates

Time and tokens come from two different places — your agents' own log rows, and the coding agent's session transcript — so it is worth being precise about how they meet.

LevelHow usage is gathered
RepositoryEvery usage row whose repo_name matches.
BranchRepository, plus a matching branch_name.
TaskRepository and branch, plus a timestamp inside that task's [start, end] span. Rows inside two overlapping task spans are split evenly between them.
AgentThe subagent the coding agent recorded for each request, joined to your agent path. Drilling to an agent shows it and everything it dispatched — the same subtree rule the tree counts use.

Each level is a strict superset of the one below it, so repository totals equal the sum of their branches, and branch totals equal the sum of their tasks plus whatever falls in no task span at all (Unattributed). Nothing is counted twice.

Per-agent cost, and the tag that makes it work

Claude Code records which subagent made every API request, in the metadata beside each subagent transcript. That is first-party data, not an inference — the reader keeps it, and this page joins it to the agent paths your own agents log.

The two sides name agents independently: LogReporter knows lead_architect/task_executor, the coding agent knows task-executor. An agent declares the link by tagging its rows:

--tags "#subagent:task-executor"

Where the tag is absent, the last segment of --agent-path is matched against the subagent type instead, with - and _ treated alike. That works when the two happen to be named the same and silently stops working the day either is renamed, so the tag is worth the one token. Requests carrying no subagent metadata at all came from the main session and are attributed to the task's root agent.

The ranking and the drill answer different questions

  • The Agent ranking shows each agent's own requests, excluding its subagents'. That is what makes the bars sum to the task total.
  • An agent drill shows that agent and its subtree, matching the row counts in the navigation tree.

So a parent's drilled figure legitimately contains its children's, while its ranking bar does not. To stop that being something you have to work out, an agent drill states the split in its header:

lead_architect  own $2.83 of $34.84 · 8.1% · subagents $32.02
task_executor   own $20.70 of $32.02 · 65%  · subagents $11.31
code_reviewer   own $6.47 of $6.47   · 100% · no subagents

The first figure is the agent's own work, the second is everything in scope including what it dispatched, and the two always reconcile. It follows the Tokens/Cost toggle like everything else.

Two logged agents sharing one context cannot be told apart. If your harness runs several agents inside a single coding-agent session without dispatching them as real subagents, no data exists that could separate their tokens — they will all attribute to the task's root agent. Time still splits correctly, because the logs record that per agent directly. Earlier versions of this page inferred agent cost from overlapping run windows; that was wrong by 10–25% against the real metadata, and counted the gaps between one agent's runs as its own.
Cost is modelled, not billed. It is what these tokens would cost at the provider's published API prices, computed at render time from the model registry — never stored, so it cannot silently become a lie when prices change. On a Pro or Max subscription the tokens draw against a plan instead, so treat this as a comparison figure, not an accounting one. An unknown model shows its tokens and a dash for cost, never a guessed rate.
