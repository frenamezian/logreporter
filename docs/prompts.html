The dashboard is only as good as the rows agents write. This repository ships the writer and the full contract; this topic is the short version, and the reason behind each rule.

The two tools

python mint_trace.py                 # lead architect only → 9f2c41a8

python log_activity.py \
  --log-type start|end|activity|issue|decision|github \
  --task "<title>" \
  --agent <name> --agent-path <lineage> \
  --trace-id <id> --log-title "<one specific line>" \
  [--log-description …] [--log-level info] [--status …]
  [--priority …] [--tags "#x #y"] [--parent-trace-id …]
  [--error-details …] [--resolved-by …]
  [--performance-metrics '{"execution_ms":12}']
  [--commit-reference <sha>] [--sync]

log_activity.py is synchronous: it validates the arguments, performs the INSERT, prints the new row id and exits. It opens the database in WAL mode with a 10-second busy timeout and retries five times with exponential backoff if it loses that timeout to another agent; a write that ultimately fails exits non-zero and says why. The repository and branch are not arguments: both are read from git in the caller's working directory, so an agent in any repository logs under the right node without being told which one it is in. The repository is named after its origin remote rather than its folder, because those drift apart — a checkout in a directory called log_reporter whose remote is frenamezian/logreporter logs as logreporter — and because the token-usage reader can only ever see the remote. --repo and --branch still exist for a directory git knows nothing about, but they are hidden from --help and outranked by git wherever git can answer.

It was asynchronous until that default lost rows. A detached child can be killed by the terminal before SQLite commits — several agent harnesses run their shell inside a job object that takes every descendant with it — while the call itself has already exited 0, and a killed child cannot write to log_activity_errors.log or anywhere else. Re-logging afterwards does not repair the damage: the rows return carrying the time they were re-written, so the task’s span collapses, and a span is what token usage is attributed to and what duration and idle time are derived from. --async restores the old behaviour for anyone who wants it, hardened to break away from the parent’s job object where Windows permits; --sync is accepted and does nothing, since it now asks for the default.

The full contracts live in orchestrator_logging_instructions.md and subagent_logging_instructions.md and are meant to be pasted into the agents' system prompts verbatim.

The contract every agent gets

You write an activity log to SQLite (table: logs) as you work.

BRACKET YOUR WORK
- First action on a task: append a `start` row.
- Last action, always, even on failure: append an `end` row with the
  final status. Durations and idle time are derived from this pair —
  a missing `end` erases everything after your last log from every
  time view.

WHILE WORKING, append one row per meaningful step:
- activity  what you did (a file read, a build, an edit)
- decision  a choice between alternatives — record the alternatives
            and why you rejected them, not just the outcome
- issue     a failure, retry or block; put the raw error text in
            error_details; when it is later fixed, log a follow-up
            issue row with resolved_by set
- github    any git operation; tag the action: #pull #push #commit
            #add #delete. For a commit, pass the full 40-char SHA as
            commit_reference, put "commit <short sha>: <title>" in
            log_title, and the full message in log_description.

ON EVERY ROW
- timestamp    UTC, 'YYYY-MM-DD HH:MM:SS'
- task_title   identical for every row of one task, character for
               character — it is a grouping key, and a title that
               drifts by one space becomes two tasks
               (repo_name and branch_name are git's, not yours)
- agent_name   your name. One lowercase token, and it must equal the
               last segment of agent_path — "Lead Architect" in one
               field and lead_architect in the other is two agents
- agent_path   your LINEAGE, not a file path: the chain of agents from
               the root down to you, e.g. lead_architect/task_executor.
               The dashboard splits this on / and renders every segment
               as an agent, so
                 projects/template_project/docs/tasks/task_0400.md
               creates five agents called projects, template_project,
               docs, tasks and task_0400.md — and hides the real one.
               The file you are working on belongs in log_title or
               log_description, never in a field
- trace_id     shared by every agent on this task; pass it to any
               subagent you spawn and set its parent_trace_id
- log_title    one line, specific: "Chose append-only over upsert",
               not "Made a decision"
- log_level    debug | info | warning | error
- status       pending | in_progress | failed | completed
- priority     low | medium | high | critical
- tags         comma-separated #tokens

HOW MANY ROWS — there is a floor as well as a ceiling.
Ceiling: do NOT log per token, per line or inside tight loops.
Floor:   a task whose only rows are start and end records that
         something happened and nothing about what. It draws one
         empty bar. Aim for 3-8 rows between the brackets: what you
         read, what you changed, each choice and the alternatives you
         rejected, anything that failed, each git operation.
If you finish with two rows you have under-logged — add what you did,
backdated with --timestamp.

Silence between rows is reported as idle time, so log when you begin
waiting on something slow.

BRACKETS ARE LOAD-BEARING. Before writing the end row, check the
start row exists — look, do not remember:
  python query_activity.py --trace <id> --fields timestamp,log_type,agent_name,log_title
A task with only one bracket has a span of zero seconds: no duration,
no idle, and no token usage attributable to it. The work is recorded
and simultaneously invisible.

IF YOU NOTICE A ROW IS MISSING, write it with --timestamp set to when
the thing happened, never when you noticed. Rows re-logged with "now"
are worse than absent — the span collapses, every derived figure goes
with it, and nothing flags it.

Trace identity — the lead architect only

YOU OWN trace_id. Subagents never mint one.

MINT A NEW trace_id (mint_trace.py) WHEN:
- You accept a new task — one trace per task_title, created on the
  `start` row and reused by every row of that task, yours and your
  subagents'.
- The same task is retried as a fresh attempt after an `end` row was
  already written: new trace, and set parent_trace_id to the trace of
  the attempt it replaces.
- Work splits into an independent task that will be reported on its
  own — its own task_title, its own trace, parent_trace_id set to
  yours.

REUSE THE CURRENT trace_id WHEN:
- You spawn a subagent TO WORK ON THIS TASK — it will log under your
  task_title. Pass your trace_id down; the subagent writes it verbatim
  and sets parent_trace_id to your trace_id. Never mint a trace per
  subagent — a subagent is not a new task, and the trace timeline is
  how a multi-agent run is read as one sequence. A subagent you are
  giving a DIFFERENT task_title is a different task: mint it a trace,
  per the third MINT rule above.
- You resume the same task after an idle stretch, a retry of a step,
  or a handoff back from a subagent.
- Anything you log about the same task_title, however far apart.

THE RULE THE OTHERS FOLLOW FROM: a trace belongs to a TASK, not to an
agent. One trace_id to one task_title, in both directions. So the
question is never "is this a subagent?" — it is "is this the same
task?"

NEVER: reuse a trace across different task_titles, mint one per log
row or per tool call, or leave trace_id empty — untraced rows still
appear in the lists but drop out of trace navigation. Three stages
logged as three task_titles under one trace read as one run with no
parent, and nothing can reconstruct which stage owned which. If the
stages are one task, give them one task_title and tell them apart by
log_title; if they are separate tasks, give each its own trace and
parent them to yours.

Log the mint itself: on the `start` row that opens a new trace, say
so in log_description (e.g. "trace 9f2c41a8 opened for this task;
parent 4d10be77") so the lineage is legible without a join.

Writing directly, without the tool

INSERT INTO logs (
  timestamp, repo_name, branch_name, task_title,
  log_type, log_title, log_description, log_level,
  status, priority, agent_name, agent_path,
  trace_id, parent_trace_id, user_id, tags,
  error_details, resolved_by, resolution_time,
  performance_metrics, input_output_hash, commit_reference
) VALUES (?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?);

Use WAL mode with a busy timeout of several seconds so concurrent agents and the dashboard's polling never fight over the lock. Keep performance_metrics a small JSON object — execution_ms, tokens, cpu_pct, memory_mb — and omit it rather than writing nulls.

How the rules map to the views. The start/end pair is every duration. agent_path is the waterfall's indentation and the "own time" subtraction. The three grouping keys are the entire hierarchy. trace_id is the detail panel's Prev/Next. Silence is idle. Every one of those is derived — nothing in the dashboard can compensate for a row that was never written.
