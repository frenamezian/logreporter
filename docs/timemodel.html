Durations are never stored. Every number on every page is derived from the log rows by script/time-model.js, so any log file produces the same figures and there is nothing to keep in sync. This topic is the implementation; Where time goes in the user guide is the same model in prose.

Entry point

window.LR = { buildModel, stream, fmt, gitAction, TYPES, CATEGORIES, GIT_ACTIONS }

buildModel(logs) → { tasks, repos, totals, gaps }

buildModel is called twice per recompute: once on the filtered rows (for the sidebar tree) and once on the drilled rows (for the pages). It is pure — same rows in, same model out.

1 · Group into tasks

The key is repo_name \0 branch_name \0 (task_title || 'Untitled task'). Timestamps are parsed as UTC: new Date(ts.replace(' ','T') + 'Z'). A row with no timestamp is skipped.

2 · Split each task into runs

Rows are bucketed by agent_path (falling back to agent_name, then '?'), sorted by time, then walked:

for each row of this agent, in time order:
    start  → close any open run, open a new one at this timestamp
    other  → if no run is open, open one at this timestamp
             append the row to the open run
    end    → set run.to and run.status, close the run

after the walk: any still-open run gets to = timestamp of its last event

run.ms    = to − from
run.depth = agent_path.split('/').length − 1

So one agent dispatched three times inside a task yields three runs. Rows arriving without a start open an implicit run rather than being dropped — the alternative loses the work entirely.

3 · Segments

Each event in a run claims the time until the next event of that run; the last event claims the time until run.to.

seg = { from, to, ms, cat, point, log }

cat   = issue    if log_type === 'issue'
        decision if log_type === 'decision'
        github   if log_type === 'github'
        activity otherwise          (activity, start, end)

point = to <= from                  zero-length: the closing `end` row,
                                    or two rows sharing a timestamp

run.by = { activity, issue, decision, github }   // Σ seg.ms by cat

Points are kept, not filtered out. They account for no time but must stay selectable and highlightable in the waterfall, which draws them as ticks.

4 · Own time (nesting correction)

kids     = runs whose path starts with `${run.path}/`
clipped  = each kid's interval ∩ this run's interval
childMs  = total length of union(clipped)
selfMs   = max(0, run.ms − childMs)

A parent stays open while its subagents work, so run.ms double-counts delegation. Subtracting the union of the descendants leaves the time the agent spent on its own work, and parent selfMs + children's spans reconstruct the parent's span. Sibling runs overlapping in true parallel are not subtracted from each other — that overlap is real concurrency, not nesting.

5 · Task totals

span    = { from: min(run.from), to: max(run.to) }
covered = union(all run intervals)
busy    = Σ length(covered)
gaps    = complement(span, covered)        → each { from, to, ms, repo, branch, task }
idle    = Σ gap.ms
agentMs = Σ run.ms
selfMs  = Σ run.selfMs

// the four coloured categories: busy, apportioned by the raw segment shares
sum = Σ over runs of (by.activity + by.issue + by.decision + by.github)
ms.activity = round(busy × Σ by.activity / sum)      … and so on

ms.wall   = span.to − span.from                       // = busy + idle
ms.idle   = idle
ms.logs   = rows in the task
ms.issues = rows with log_type === 'issue'
Why apportion. Raw by sums are per-run, and nested runs count the same wall-clock minutes twice (the parent waiting, the child working). Summing them directly would make a task's coloured bar longer than the task. Scaling them onto busy preserves the shape — the ratio between categories, exactly as the segments reported it — while keeping the bar's length equal to real elapsed time. The consequence to remember: at task level and above, a category figure is apportioned wall clock, not a sum of agent time. Only run.by is raw.

Task status is the status on the last end row that carries one, else in_progress. largestGap and trace (the first non-empty trace_id) are stored alongside.

6 · Roll-up

branch.ms = Σ task.ms      // field by field, including wall and idle
repo.ms   = Σ task.ms
totals    = Σ task.ms  +  { tasks, done, open, failed }

Every level is a plain field-wise sum of the task buckets, so idle / wall is comparable at any depth. Note that a repository's wall is the sum of its tasks' walls, not its own first-to-last span: two tasks running the same afternoon count twice, because the question is how much task time the repository represents. Repositories and branches are sorted by wall descending; tasks by most recent end.

7 · The chronological stream

stream(logs, model) sorts the rows ascending and emits {kind:'day'}, {kind:'gap'} and {kind:'log'} rows. A gap is emitted only between two consecutive rows of the same task, and only when the model actually has a gap starting at the earlier row's timestamp — gaps are never inferred from row spacing. The Chronology page reverses the finished array for newest-first, so day headers and gaps stay attached to the right entries.

8 · Formatting

fmt(ms):  < 60s → "42s"      < 60m → "37m"      else → "1h 31m"
          null / NaN → "—"

Rounded to the nearest second before bucketing, so a 59.6s span reads "1m". Detail-panel trace offsets use their own finer scale — ms, s with one decimal, m, h — because the interesting differences there are sub-second.

Consequences worth knowing

  • A run whose end row never arrived is closed at its last event, so everything after that point is invisible to the model — and shows up as idle.
  • A task with a single entry has zero wall clock and contributes nothing but a row count.
  • Time spent by an agent that logs nothing is reported as idle. That is the honest reading, and the reason the logging contract asks agents to log before waiting on something slow.
  • A task title that drifts between rows becomes two tasks, each with its own span, and the gap between them becomes nobody's idle.
