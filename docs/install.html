Clone it, make a database, serve it — then tell your agents to log into it. The first half takes four commands; the second half is the one that matters, because an installed dashboard with unmodified agents shows you an empty tree forever.

1 · Clone

git clone https://github.com/frenamezian/logreporter.git
cd logreporter

2 · Create the database

activity_logs.db is deliberately not in git. It is runtime data that several agents write to continuously, and a tracked binary would produce diffs nobody can merge. So a fresh clone has no database until you make one — pick one:

bash seed/init_db.sh      # A — start from the bundled sample
python seed/new_db.py     # B — start empty

A gives you 148 rows across three repositories, so every page has something in it — the right choice for a first look. B is what you want for real use. Either way you end up with activity_logs.db in the repository root, in WAL mode so several agents can write while the dashboard reads. You can also start from the sample and clear it later from the Maintenance page.

2b · Protect it

One command, and it is worth the ten seconds. activity_logs.db is the only file here that nothing can reconstruct:

git config core.hooksPath .githooks

That enables a pre-commit guard which refuses to commit the log database or the usage cache — git add -A is one keystroke from sweeping a live database into history. It is per-clone config, not something the repository can set for you, so a fresh clone needs it again.

Two other protections are already in place and need nothing from you:

  • Neither database is in .gitignore. That looks backwards and is not: git silently overwrites an ignored file when a checkout wants to write one there, and refuses outright for an untracked, unignored one. Eleven commits in this repository's history still carry an old copy of activity_logs.db, and a checkout of one of them destroyed a live database. Unignored, git aborts instead. The cost is one line each in git status.
  • serve.py snapshots both into backups/ on every start and before every destructive operation, keeping the last ten of each. It uses SQLite's online backup API, so a snapshot of a database being written to is still consistent. Empty databases are skipped.

The two databases, side by side

They are protected identically. They differ only in what they contain and what a loss costs — and the protections deliberately ignore that difference, because a rule with a per-file exception is a rule that gets applied wrong.

The one asymmetry worth knowing is the watermark table inside token_usage.db. It records how far the reader got through each transcript, and it is not re-derivable in the cheap sense: losing it does not lose data, but it turns the next import into a full re-read of every session file on the machine. That is why Rebuild usage takes a snapshot first, exactly as a delete does.

3 · Start the dashboard

python serve.py           # any OS → http://127.0.0.1:8250/index.html
python serve.py 9000      # any port, if 8250 is busy

On Windows, double-clicking start_LogReporter.bat does the same thing and opens your browser for you.

Do not open index.html by double-clicking it. On a file:// origin the browser's fetch() cannot read activity_logs.db at all, and the dashboard falls back to demo data — quietly, apart from the grey dot in the header. It has to be served over http://.

serve.py binds to 127.0.0.1 only, so nothing is exposed to your network. It is not just a static server: it also provides the write endpoints the dashboard cannot perform itself — the row-level delete behind the Maintenance page, and the usage re-import. Serving the folder with python -m http.server instead will render every page correctly and silently break both.

4 · Check it works

Open http://127.0.0.1:8250/index.html. The button at the top right should read activity_logs.db with a lit dot, and the header should show a row count. If it says Demo data, the page is not being served over http:// or the file is missing.

Telling your agents to log — the part that makes it work

Everything above installs a viewer. Nothing appears in it until your agents write rows, and they will not do that on their own: you have to add logging instructions to every agent's prompt. The goal is one sentence — every agent in every repository appends to the one activity_logs.db in your LogReporter clone.

The one rule: agents call log_activity.py by absolute path, from whatever directory they happen to be working in. The writer appends to the activity_logs.db sitting next to itself, never next to the caller. That is the whole mechanism — one canonical copy of the writer, one canonical database, and any number of repositories calling into it. No per-repository configuration, no environment variable, no copy of anything.

5 · Get your absolute path

python -c "import os; print(os.path.abspath('log_activity.py'))"

Run it from inside your clone. Substitute the result everywhere <LOGGER> appears below; do the same for mint_trace.py as <MINTER>.

OSLooks like
WindowsC:/Users/you/dev/logreporter/log_activity.py
macOS/Users/you/dev/logreporter/log_activity.py
Linux/home/you/dev/logreporter/log_activity.py

Forward slashes work fine on Windows and avoid backslash-escaping headaches inside prompts.

6 · Smoke-test it from a different repository

Do this before editing any prompt. Stand in some other project and write one row by hand:

cd ~/dev/some-other-project
python <LOGGER> --sync --log-type start \
  --task "Smoke test" --agent me --log-title "Hello from another repo"

It prints a row id. Refresh the dashboard and a node appears under that repository's name and its current branch — neither of which you passed:

some-other-project              ← repo name, from git
  └ feat/whatever-you-are-on    ← current branch, from git
      └ Smoke test              ← --task
          └ me                  ← --agent

That is --repo and --branch auto-deriving from git in the caller's working directory, and it is the reason one prompt works everywhere. If this step fails, fix it here — no prompt edit will make it work later. Delete the test row from the Maintenance page when you are done.

7 · Give your lead agent the orchestrator prompt

Paste the contents of orchestrator_logging_instructions.md (repository root) into your lead agent's system prompt, with two edits:

  1. Replace every python log_activity.py and python mint_trace.py with the absolute paths from step 5.
  2. Delete the --repo and --branch flags. The shipped file hardcodes --repo logreporter --branch main, because that is what this project's own agents used. Dropping them is exactly what makes the prompt portable: git then fills both in correctly, per repository and per branch, with no editing.

What the prompt asks the agent to do, in short:

python <MINTER>                     # mint ONE trace_id per task — lead only
python <LOGGER> --log-type <type> --task "<title>" \
  --agent <name> --agent-path <lineage> --trace-id <id> \
  --log-title "<one specific line>" [--log-description "..."] \
  [--log-level info] [--status in_progress] [--tags "#x #y"] \
  [--error-details "..."] [--commit-reference <sha>]
  • Bracket every task — a start row first, an end row last even on failure, carrying the final --status.
  • One row per meaningful step between them: activity, decision, issue, github. Not per token, not per line, not inside loops.
  • The lead owns trace identity. One trace per task, reused by every row of that task including its subagents'.

8 · Give every subagent the subagent prompt

Same treatment for subagent_logging_instructions.md: absolute path, no --repo/--branch. The lead fills in the placeholders when it dispatches:

PlaceholderFilled in withExample
<name>the subagent's --agentcode_reviewer
<lineage>its --agent-pathlead_architect/task_executor/code_reviewer
<trace_id>the lead's trace, verbatim9f2c41a8
<parent_trace_id>the lead's trace9f2c41a8
<task_title>the lead's exact task titletask_0350 - Fix docstring
Three things that quietly ruin the output if you get them wrong. A missing end row erases everything after the agent's last log from every time view — the run is closed at its last event. task_title is a grouping key matched character for character, so a title that drifts by one space becomes two tasks with two separate wall clocks. And --agent-path is what builds the agent tree, the waterfall's indentation and "own time"; get the lineage right and the whole time breakdown is right.

Optional · tokens and cost

The Metrics page can also report what the work cost. Nothing needs configuring and your agents are not involved — the numbers are read from the session transcripts your coding agents already write, so this works on history that predates the feature.

python usage_reader.py

That builds token_usage.db beside the log database. After the first run you never need the command again: Refresh usage and Rebuild usage on the Maintenance page do the same thing through serve.py. The file is a pure cache — delete it, re-run the reader, and you are exactly where you started. Only activity_logs.db is worth backing up.

Prices come from a registry checked into the repository, so Models & pricing works immediately whether or not you ever build the usage cache.

Troubleshooting

SymptomCause and fix
Header says Demo dataNot served over http://, or activity_logs.db is missing. Start it with python serve.py and check the file exists.
activity_logs.db not found at … from an agentThe database was never created. Run step 2.
Agent says it logged, nothing appearsA default (synchronous) call that returned 0 has written its row, so check the agent is calling the absolute path you think it is, and is not passing --async. Under --async the write happens in a detached child that the terminal can kill before SQLite commits — the call still exits 0 and nothing reaches log_activity_errors.log, because a killed process cannot report itself. Drop --async.
Rows land under the wrong repositoryThe agent's working directory is not what you think, or the prompt still passes --repo/--branch. Delete those flags, or cd first.
One task appears twiceTwo spellings of the same task_title. It is a grouping key, matched exactly.
A task shows huge idle timeSomething ran without logging, or an end row never arrived. Both are real findings, not display bugs.
Deleting does nothing, or says NOT savedThe page is served by something other than serve.py, so the delete endpoint is missing.
Nothing renders; the console shows a CDN errorsql.js could not be fetched. See below.
Port 8250 is busypython serve.py 9000 — any port works.
A change to the code does not show upAssets are cached. Bump the ?v= query in index.html, or hard-reload.

Running fully offline

Download sql-wasm.js and sql-wasm.wasm (sql.js 1.10.3), drop them next to index.html, and point the two constants at the top of script/db.js at the local copies. That is the only remote dependency in the project — there is no framework, no charting library, no icon package and no web font to account for. The diagram above is a checked-in SVG for the same reason.
