LogReporter is a single static page that reads an agent activity log — a SQLite file, activity_logs.db — directly in your browser. There is no server and no upload: the file is parsed in place and every view is computed from the rows in memory.

On first load you are looking at the bundled demo dataset, so every page has something in it. To read your own log:

  1. Open the data-source button in the header — it reads Demo data until a file is loaded.
  2. Choose Open activity_logs.db and pick your file (.db, .sqlite, .sqlite3).
  3. The status dot turns accent-coloured and the row count appears. Every page now reflects your data.
  4. Turn on Auto-poll if agents are still writing — the file is re-read whenever its modified time changes.

Auto-poll needs a browser that supports file handles (Chromium-based). Elsewhere, press Refresh and re-pick the file.

A good first pass: leave the filters empty, skim Hierarchy to see which repositories carry the work, then hit Where time goes to see how much of that wall-clock time was idle.

The left panel holds two collapsible sections: Filters and Navigation. Both narrow what every page shows.

Filters are a flat AND of search text, repository, branch, agent, log type, git action, level, status, priority and a date range. Each active filter appears as a chip you can dismiss; the count next to the section title tells you how many are on even when the section is collapsed.

Navigation is the repository → branch → task → agent tree. A single click scopes the whole dashboard to that node and writes it into the breadcrumb; a double click scopes it and collapses the node so you keep your place. Clicking an agent toggles that agent on and off within its task.

The tree is deliberately built from the filtered set before your drill scope is applied, so every sibling stays visible and one click away — you never have to walk back up the breadcrumb to move sideways. All repositories clears the drill; the breadcrumb above the content does the same at any depth.

The « button collapses the panel to a rail; the filter icon on the rail brings it back with the filter section open.

The default page: one card per repository, nested down through branches, tasks and finally the individual log entries.

Every level carries the same summary vocabulary — a stacked bar showing how its wall-clock time splits into activity, issue, decision, GitHub and idle, then the wall-clock total and the idle share. Badges count logs and issues. Time → jumps to Where time goes already scoped to that node.

Task rows list entries in ascending time with type, agent, title, a description snippet and level. Clicking a row opens the detail panel on the right; the row grid drops to time / type / entry while the panel is open so nothing is truncated.

Expand all and Collapse all act on the rows in scope only — the navigation tree keeps its own open state.

One flat timeline across everything in scope, so interleaved agents read in the order they actually ran. Day headers carry the entry count; each entry shows its clock time, a coloured dot for its type, the agent, where it ran and how long its slice of the run lasted.

Idle stretches are rows in their own right — a dashed rule labelled with the duration and the branch and task nobody was logging against. That is the point of this page: the silence is as legible as the activity.

Order is newest-first by default. The stream renders the first 500 rows in scope; narrow the filters or drill down if you hit that ceiling.

The stat cards give totals for the scope: wall-clock, agent time (agents overlap, so this can exceed wall-clock), idle, issue time and GitHub time. Below them, one bar per item at whatever level you have drilled to — repositories, then branches of a repository, then tasks on a branch, then agents on a task. Clicking a bar drills one level further.

Drilled to a single task, the waterfall appears: one row per agent run, indented by agent_path, positioned horizontally by real clock time and segmented by log type. The idle row underneath shows the gaps no run covers, and the largest single gap is called out in words.

The closing table ranks the longest idle gaps anywhere in scope; each row jumps to its task.

Aggregates over the same filter and drill scope as everything else — nothing here is computed over the whole database unless the scope is the whole database.

  • Task counts by state: open, completed, failed, plus the idle share of wall-clock.
  • Entries by log type, and GitHub operations broken down by git action (read from the tags on each github log).
  • Median task duration per repository — median, not mean, because one abandoned task otherwise dominates.
  • Open issues and escalations as cards; clicking one jumps to that entry in the hierarchy with its ancestors expanded.
  • Agent time by agent_path, with the entry count alongside.

Logs are retained until you delete them — there is no automatic rotation, on purpose.

Delete takes its own scope (repository, branch, older-than date, log type) that is independent of the page filters, shows how many rows match, and asks for confirmation before removing them. Rows are deleted from the database held in memory; use Save database copy to write the shrunken file back out. Nothing on disk changes until you save.

Export honours the page filters and drill scope instead, so you can carve out one branch or one date range as CSV or JSON.

The stored volume table is the only view that always reads the entire database: rows and issue counts per repository and branch with the oldest and newest timestamps, so you can see what is worth pruning.

Clicking any entry — in the hierarchy, the chronology, a metrics card or the waterfall — opens the detail panel on the right.

It shows the full description, tags, the raw error text when the entry carries one, and the agent path as a chain from the root agent down to the one that wrote the log. The Record grid lists the stored fields verbatim, including anything parsed out of performance_metrics: execution time, tokens, CPU and memory.

Underneath, the trace timeline lists every entry sharing this trace_id with offsets from the first one, so a multi-agent run reads as a single sequence. Prev and Next in trace step through it without leaving the panel.

A static page over a local SQLite file. No backend, no build step, no network calls except the one CDN fetch for the SQLite engine.

activity_logs.db  (written by the agents)
      │
      │  File System Access handle, or a file input
      ▼
sql.js (SQLite compiled to WASM, loaded from CDN)
      │  SELECT * FROM logs ORDER BY timestamp DESC
      ▼

The database is read once per load or poll and never queried per view — every page is a pure function of the in-memory row array. That keeps interaction instant and means a 50k-row file behaves the same as a 500-row one.

Deletions execute against the in-memory database as well as the row array; Save database copy exports the mutated bytes. The original file is never written to.

The one hard invariant: each agent brackets its work with a start row and an end row carrying the same repo, branch, task and agent_path. Durations and idle gaps are derived from those pairs; without them a run has no span and contributes no time.

The dashboard issues exactly two statements. Everything else is computed in JavaScript over the result of the first.

-- read (on load, on Refresh, on each poll tick)
SELECT * FROM logs ORDER BY timestamp DESC;

-- delete (Maintenance, after confirmation; in memory until saved)
DELETE FROM logs WHERE id IN (…);

Filtering in SQL was rejected deliberately: round-tripping WASM per keystroke is slower than filtering an array, and a single read keeps the file lock brief while agents are writing.

If you would rather query the file directly, these mirror what the pages show.

-- run spans per agent (the basis of every duration)
SELECT repo_name, branch_name, task_title, agent_path,
       MIN(timestamp) AS started, MAX(timestamp) AS ended,
       COUNT(*)       AS entries
FROM logs
GROUP BY repo_name, branch_name, task_title, agent_path
ORDER BY started;

-- unresolved issues, worst first
SELECT timestamp, repo_name, branch_name, agent_name, log_title, error_details
FROM logs
WHERE log_type = 'issue' AND resolved_by IS NULL
ORDER BY CASE log_level WHEN 'error' THEN 0 WHEN 'warning' THEN 1 ELSE 2 END,
         timestamp DESC;

-- git activity by action
SELECT CASE WHEN tags LIKE '%#push%'   THEN 'push'
            WHEN tags LIKE '%#pull%'   THEN 'pull'
            WHEN tags LIKE '%#commit%' THEN 'commit'
            ELSE 'other' END AS action, COUNT(*) AS n
FROM logs WHERE log_type = 'github' GROUP BY action ORDER BY n DESC;

Two indexes are worth having on a large file: (timestamp) for the read, and (repo_name, branch_name, task_title) for grouped queries. Writers should run in WAL mode with a busy timeout so a poll never blocks an agent.

Durations are never stored — they are derived, in time-model.js, so that any log file produces the same numbers.

  • Run — one start→end pair for one agent_path within one task. Its length is the run's agent time.
  • Segments — the entries inside a run split it into consecutive slices, each attributed to the log type that opened it: activity, issue, decision or github. That is what colours every stacked bar.
  • Wall-clock — first to last event of the task, regardless of who was working.
  • Idle — the complement of the union of all runs inside that wall-clock span. Overlapping agents are unioned first, so parallel work never manufactures idle time.
  • Agent time — the sum of run lengths. It can exceed wall-clock when agents overlap; that ratio is shown on the stat card.

Branch, repository and global totals are sums of task totals, so an idle share is always comparable across levels. The largest gap per task is kept separately for the waterfall callout and the gaps table.

Consequences worth knowing: a run whose end row never arrived contributes no time; a task with a single entry has zero wall-clock; and time spent by a process that logs nothing counts as idle, which is the honest reading.

The interface follows the Nocturne system: a near-neutral dark ground, Inter at medium weight, 8px radii, and the accent used as a line, a tint or a glow — never as a flood. Every colour, size and space comes from the design tokens.

Activity Issue Decision GitHub Idle

Idle is hatched rather than coloured — absence should not read as another kind of work.

Layout rules the pages share: one scroll region per page under a fixed header and breadcrumb; numbers tabular-figure and right-aligned; identifiers (repository, branch, agent) monospace and verbatim while closed enums are humanised; a single accent left border marks the selected row; and tags carry level, status and type rather than coloured text.

Bar widths are the one thing that cannot be written as a literal style, since a width is a percentage of a measured total. Bars are marked up with data-bar or data-geo attributes and sized after paint, which keeps the markup static and the page legible before any data has loaded.

What clicking does, shell-wide:

  • A page tab — swaps the content region only. Filters, drill scope, tree open/closed state and the selected entry all survive, so switching pages is a change of lens, never a reset.
  • A tree node — single click sets the drill scope (and writes the breadcrumb); double click does that and collapses the node. An agent leaf toggles.
  • A breadcrumb — truncates the drill to that depth. All repos clears it.
  • A filter or chip — recomputes rows in scope; the header count and every page follow within the same frame.
  • Any entry row, anywhere — selects it and opens the detail panel; the content region reflows narrower rather than being overlaid, and dense row grids drop their optional columns.
  • The « rail button — collapses the left panel to a 46px rail carrying just the filter badge; the filter icon restores it with filters open.
  • ? — replaces the whole body with this guide and remembers the page you left, which Back to dashboard returns to.

The dashboard is only as good as the rows agents write. Give every agent this contract — as a system prompt fragment or a tool description — and the derived views work without further configuration.

You write an activity log to SQLite (table: logs) as you work.

BRACKET YOUR WORK
- First action on a task: append a `start` row.
- Last action, always, even on failure: append an `end` row with the
  final status. Durations and idle time are derived from this pair —
  a missing `end` erases your work from every time view.

WHILE WORKING, append one row per meaningful step:
- activity  what you did (a file read, a build, an edit)
- decision  a choice between alternatives — record the alternatives
            and why you rejected them, not just the outcome
- issue     a failure, retry or block; put the raw error text in
            error_details; when it is later fixed, set resolved_by
- github    any git operation; tag the action: #pull #push #commit
            #add #delete

ON EVERY ROW
- timestamp    UTC, 'YYYY-MM-DD HH:MM:SS'
- repo_name, branch_name, task_title  identical for every row of one
  task, character for character — they are the grouping keys
- agent_name   your name
- agent_path   your lineage, e.g. lead_architect/handler_dev
- trace_id     shared by every agent on this task; pass it to any
               subagent you spawn and set its parent_trace_id
- log_title    one line, specific: "Chose append-only over upsert",
               not "Made a decision"
- log_level    debug | info | warning | error
- status       pending | in_progress | failed | completed
- priority     low | medium | high | critical
- tags         comma-separated #tokens

DO NOT log per token, per line or inside tight loops. One row per
step a human would want to see. Silence between rows is reported as
idle time, so log when you begin waiting on something slow.

The lead architect — the root agent, the only one with no parent — owns trace identity. Append this to its prompt only:

YOU OWN trace_id. Subagents never mint one.

MINT A NEW trace_id (random hex, 8+ chars) WHEN:
- You accept a new task — one trace per task_title, created on the
  `start` row and reused by every row of that task, yours and your
  subagents'.
- The same task is retried as a fresh attempt after an `end` row was
  already written: new trace, and set parent_trace_id to the trace of
  the attempt it replaces.
- Work splits into an independent task that will be reported on its
  own — its own task_title, its own trace, parent_trace_id set to
  yours.

REUSE THE CURRENT trace_id WHEN:
- You spawn a subagent for this task. Pass your trace_id down; the
  subagent writes it verbatim and sets parent_trace_id to your
  trace_id. Never mint a trace per subagent — the trace timeline is
  how a multi-agent run is read as one sequence.
- You resume the same task after an idle stretch, a retry of a step,
  or a handoff back from a subagent.
- Anything you log about the same task_title, however far apart.

NEVER: reuse a trace across different task_titles, mint one per log
row or per tool call, or leave trace_id empty — untraced rows still
appear in the lists but drop out of trace navigation.

Log the mint itself: on the `start` row that opens a new trace, say
so in log_description (e.g. "trace 9f2c41a8 opened for this task;
parent 4d10be77") so the lineage is legible without a join.

The append itself, with the columns in the order the dashboard expects:

INSERT INTO logs (
  timestamp, repo_name, branch_name, task_title,

  error_details, resolved_by, resolution_time,
  performance_metrics, input_output_hash
) VALUES (?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?);
